# Sync provider reference

This reference is for administrators and developers. For setup instructions written for players, see [Using LANLauncherNG](using-lanlauncher.md).

## Provider model

Settings → Provider can add a provider manually or import provider entries from a `bootstrap.json`. The importer reads the top-level `items` array, imports only entries with `is_game_provider: true`, validates their required fields, and rejects duplicate IDs without replacing existing providers. IDs that consist only of dots (`.`, `..`) are rejected because they would resolve to the library root or its parent. The import is atomic: if applying an imported provider to its sync engine fails, LLNG detaches and removes all entries from that import, so the same file can be imported again after the cause is fixed.

The Status overview lists the Resilio and Ouisync process IDs separately under the overall sync service card.

The Ouisync panel also shows the settings of the selected repository: DHT, Peer Exchange, and Use Cache Servers. DHT and Peer Exchange can be changed while repository sync is enabled. Cache-server mirroring uses Ouisync's production cache host and can be changed only when the local repository has write access; read-only repositories show the setting as unavailable. The mirror state is queried from the cache server only for writable repositories, with a short timeout, and is cached for several minutes. Offline, for example at a LAN party without Internet access, the inventory stays available and the setting is shown as unavailable instead. Changes are applied to Ouisync directly and the panel rereads their actual state.

The repository table exposes the local Ouisync database path as a hover tooltip. Repository contents can be copied to disk under the mapped game folder by choosing a relative destination directory. Read-only repositories can also be mounted beneath `<library>/<game_id>/ouisyncmount/<repository-name>`; the operating system mount remains read-only because LLNG permits this only for repositories opened with read access. If a normal unmount cannot release open handles, **Force unmount** restarts the Ouisync process, briefly interrupting synchronization for all repositories. It is refused while a game download is running, so installs are not cancelled implicitly, and it restores the previous mount root after the restart. Ouisync's progress fraction counts locally present blocks against distinct block IDs referenced by repository snapshots, rather than files. A value such as 98% therefore says some indexed blocks are not present locally; it does not identify whether those blocks are still arriving or are retained by older snapshot references. Ouisync 0.10.x has a known accounting defect after updates to an existing repository: unchanged blocks reused by the new snapshot can stay flagged as missing even though they are stored locally, so the counter stalls (for example at 98%) and older snapshots are kept as fallbacks. When the counter stops changing for 60 seconds, LLNG therefore reads every file of the current snapshot. If all reads succeed, the sync counts as complete, the update is applied, and Provider UIs shows **content complete (verified)**. If data is genuinely missing, LLNG keeps waiting and checks again with a growing interval (up to 15 minutes). A fresh replica reports 0/0 blocks until the first snapshot index arrives; LLNG shows this as 0%, not as complete. A game is installed only after its download job has received the complete snapshot, not when the block counter alone looks finished. A repository can come back paused after a restart, for example when Ouisync reopened it after its store directory was replaced. A game download or installation interrupted by quitting LLNG therefore keeps its download state and resumes automatically after the next start; failed resume attempts are retried with a growing interval (up to 15 minutes). Pausing a download yourself, or uninstalling the game, ends this.

If a repository still has no local block 60 seconds after its download started, LLNG nudges it automatically: it re-adds the known peers (LAN server, paired peers, manually added peers) and restarts the DHT lookup for repositories that use DHT. From the second attempt on, it also reconnects the repository (sync off and on again), which rebuilds its peer connections and pending requests. Attempts repeat with a doubling interval of up to 15 minutes until blocks arrive and are logged as `ouisync_repository_nudged`. Ouisync has no command to request missing data again, so these steps cannot fix every stall; restarting Ouisync remains the last resort. **Nudge sync** in the repository settings runs all steps immediately for the selected repository. It interrupts only that repository for a moment.

Selecting a repository also shows the **Peers** card: every peer known to Ouisync with its address and transport (QUIC or TCP), how it was found (added manually, connected to this device, local discovery, DHT, or Peer Exchange), its connection state, current download/upload speed, and bytes received/sent. Ouisync 0.10.x reports peers for the whole session, not per repository, so the list is the same for every repository. If peers are not found automatically, for example in an isolated network, add one manually as `IP:port` (QUIC is assumed) or `quic/IP:port` / `tcp/IP:port`. Only literal IPv4 or bracketed IPv6 addresses are accepted, no host names. Ouisync keeps manually added peers across restarts; they can be removed again in the list. The card also shows this device's listener addresses; on another device, enter this device's LAN IP address with that port. LAN pairing adds its own peers automatically and adds them again after removal.

When automatic sync is enabled, LLNG starts the Ouisync process during first-run setup even before the library path is saved. It waits to attach/materialize repositories or run game tasks until the library path is ready. Resilio remains gated on a configured library path.

Validated local-index entries assigned to Ouisync are reconciled into the main catalog. Installable titles such as 0 A.D. therefore appear in the start overview with their missing/download state even when the legacy `game.db` is disabled.

LLNG uses the bundled Ouisync CLI as the default provider for the global OpenSourceGameIndex catalog. LLNG supervises it as a child process and controls it through Ouisync's bundled asynchronous Python session client over its authenticated local socket. Provider status and traffic are shown in the header and Status tab. LLNG verifies v2 index signatures against a root-signed `trusted-publishers.json`, persists registry sequence/digest state locally, rejects rollback, and does not expose Ouisync read tokens in ordinary catalog payloads. Builds without a provisioned catalog-root key fail closed for v2 catalogs. Each game has a separate Ouisync repository; its owner may keep that repository on a different machine from the central `ng_provider` repository. The signed index carries only the game's read-only capability and expected repository hash. The central provider repository distributes the signed index, trust registry, update files, and catalog media; it does not need mirrored per-game repositories or a `game.db` for removals. LLNG materializes selected game repositories under `<library>/<game_id>/.ouisync/<game_id>` by default; an optional repository storage root can place them on another disk. Changing the root applies to new repositories; existing repositories are reused from their previous root and are not moved automatically. LLNG mounts a selected repository only for install/update, extracts the archive directly from that mount into writable `local/`, copies metadata, media, and launch files needed after unmount, and then unmounts. Users can remove repository data later while retaining the extracted game. Private LAN shares also get one repository per selected game folder, including local-only folders that are not in the global database. LLNG copies shareable files from the game folder through a temporary writable mount, excludes `local/`, and flattens `.ouisync` content into the repository root; `.ouisync` wins on duplicate relative paths. It issues a read-only key and publishes it with the game entry in the local LAN catalog. Linux uses FUSE. Windows includes the VFS-enabled CLI and Dokan runtime; setup offers the signed Dokan kernel driver as a checked-by-default component that requires administrator approval and remains installed after temporary mounts end. See [ADR-0003](../shared/adr/ADR-0003.md); physical Windows mount/install verification remains open.

The **Ouisync** tab in Provider UIs is LLNG's native repository view. It distinguishes a running process from an available session and imported repositories. The table reports Ouisync's local/total block counts, transfer rates, and active/known peer counts from the Ouisync session. The block counts are not byte sizes; peer counts are session-wide, not per-repository, and the current session API does not report remote byte size. Generic Ouisync names are matched against trusted extra-sync tokens so built-in repositories display their game ID, such as `ng_provider`. **Available** reflects whether the Ouisync session is running; Ouisync has no Web UI URL, so URL presence is not a useful availability check for it. LLNG registers each repository parent as an Ouisync store directory before creating or reopening it. This is needed for the daemon to rediscover repositories stored under game/library folders after startup, including LAN seeds and the LAN catalog. On start, LLNG keeps the store directories Ouisync already persisted and only adds its own; replacing the list would make Ouisync close repositories in the dropped folders, so LAN seeds or installed games would stop being shared after a restart. At startup and during watchdog checks, LLNG verifies that the trusted `ng_provider` repository is attached by comparing its token's repository hash with the active session. If it is missing, LLNG retries attachment with a bounded backoff. The diagnostic actions inspect provider startup, the trusted `ng_provider` bootstrap capability, and whether its repository hash is attached. **Reset and reconnect ng_provider** closes its repository, deletes the local `<library>/ng_provider` cache, and reattaches it using the integrated trusted bootstrap token; it does not alter the remote repository. Ouisync actions never fall back to Resilio: without a running Ouisync provider they report `sync_provider_unavailable`. Each action opens a live log dialog. A failed automatic seed initialization is also written to the application log. The panel reads the local index and Ouisync session and does not fetch catalog data from the Internet or expose repository tokens. Resilio remains an optional compatibility provider.

After the `ng_provider` repository is attached, the watchdog waits for its complete Ouisync snapshot and copies repository files into ordinary files under `<library>/ng_provider`, including update packages, images, and videos. The Ouisync database remains under `.ouisync`. Every minute LLNG compares the synced `update/index.json`, `update/update-manifest.json`, and `update/trusted-publishers.json` with the materialized copies; a changed marker triggers a staged update of the provider files and removes stale files recorded by LLNG. Image and video revisions are published with a new signed index revision. Unchanged trees are not copied again.

Resilio remains available for existing catalog entries that explicitly select it. Ouisync is the default for the public OpenSourceGameIndex and the private LAN workflow. LLNG owns LAN discovery, pairing, and share selection; it does not require an Internet connection.

LLNG **Launcher mode** controls its private LAN workflow:

- **Client** receives the shared LAN catalog and downloads game folders when requested.
- **Server** includes the client behavior and can publish selected library folders and server settings.

The Ouisync CLI and Python `ouisync.session` binding are bundled with LLNG. Resilio binaries and license material are locally supplied and are not included in the source repository.

The installed `config/bootstrap.json` seeds the built-in `ng_provider` entry. Installers can also carry an optional installer-side `bootstrap.json`, stored as `config/optional-bootstrap.json`; LLNG seeds entries from both files. The local publisher file `ng_provider/bootstrap.json` is excluded from version control and copied beside the installer only when present, so legacy entries such as `eti_launcher` can be included for a specific distribution without shipping them by default. When an entry previously seeded from an optional file is no longer present in either bootstrap, LLNG removes that seeded row on startup; manually added entries are retained.

## Set up the LAN server

The server and clients need separate LLNG installations, a reachable shared network, and a configured library. The server should have the game files it offers. Save **Server** mode before configuring shares.

In Settings, share only the game folders intended for the event. Folders already owned by a distribution provider are excluded, including OpenSourceGameIndex, Resilio, Ouisync, and other non-local provider entries. A local catalog entry can be shared when its `<library>/<game_id>` folder exists. OpenSourceGameIndex folders stay excluded while a removed game is still installed. Each shareable folder needs a unique game ID and title in `metadata.json`; the server editor creates or updates this file. Cover paths must point to local files inside the catalog. LLNG checks IDs against its local database, the LAN index, and available official provider databases before accepting a new entry.

LLNG writes the catalog to `<library>/locallansync/.ouisync/index.json` using the Open Source Game Index structure. Ouisync serves this catalog continuously. Each shared game's shareable game-folder files are copied through a temporary writable mount into a separate per-game repository, stored under `<repository_root>/<game_id>/.ouisync/lan-repository` (or the library root when no separate path is configured). Files from `.ouisync` are flattened into the repository root. The repository excludes `local/`, its own database, and LLNG staging files. A client downloads the catalog during pairing and syncs each game repository only when requested. Installation temporarily mounts the repository, extracts the archive into writable `local/`, copies required files to the game folder, and unmounts it. Removing a share withdraws it from the catalog and pauses its server-side Ouisync seed.

Server game availability and event links are stored in `<library>/locallansync/settings.json`. The file is written atomically to avoid exposing partial JSON. Clients retain their last valid copy if an update is incomplete or invalid. Until a valid LLNG server snapshot arrives, the existing `launcher.ini` integration remains the fallback. Disabling a game hides it from clients except where it is already installed.

## Pair clients

The server advertises itself on the local IPv4 network using UDP port `28384`. Discovery can be broadcast or sent to a known IPv4 address. Discovery only identifies a server; it does not enroll a device. Pairing verifies an explicit four-digit code and returns an authenticated, read-only Ouisync catalog token, repository hash, and peer listener addresses. The client stores this capability locally and uses it to download `locallansync`.

This pairing flow is exclusively for private LAN Server sessions that share custom/event games. It is not used for global OpenSourceGameIndex distribution: clients obtain read-only repository tokens from the signed index and do not require an online owner or owner-side device approval. Private LAN game repositories disable global DHT discovery and use local discovery, peer exchange, and paired peer addresses.

The pairing response HMAC covers the canonical capability payload, both device identities, and the request nonce. The client also includes its Ouisync listener ports in the authenticated request. The server binds those ports to the observed client IPv4, persists the paired-client endpoint roster, and returns known peer endpoints to subsequently paired clients. Each client adds the owner's and paired peers' endpoints to Ouisync, so a client that already paired can continue downloading from another paired client after the owner stops. The roster is stored with the pairing state and survives owner restarts. The opt-in three-instance integration test verifies pairing, owner-to-client transfer, and client-to-client transfer after the owner stops. It has been exercised through the host's LAN IPv4; separate physical machines should still be checked before release.

The code is reusable by multiple clients, persists across launcher restarts, and expires after three days. Renewing it invalidates the previous code immediately. Five distinct failed proofs temporarily block pairing for one minute. A short numeric code is suitable for a trusted LAN event, not for protecting against an observer who can capture and brute-force LAN traffic. The LLNG control API remains loopback-only; it is not exposed for discovery or remote administration.



## File direction and peer seeding

The server is authoritative for shared game sources. It publishes updates; client-side edits and deletions are not sent back. A client with a complete repository can seed another client after the owner goes offline, provided Ouisync can reach that peer. Pairing supplies peer endpoints automatically; Ouisync's multicast local discovery remains an optional supplement and has not been verified between separate physical LAN devices.

The launcher creates or activates a game's Ouisync repository only when a player requests it. It waits for the repository snapshot, mounts it for the installation operation, and unmounts afterward. **Remove downloaded data** deletes that client's repository while leaving the installed game in place.

## Resilio network controls

The Settings actions **Resilio LAN Mode** and **Resilio Internet Mode** apply or remove host firewall restrictions for Resilio traffic. The Linux firewall action may ask for administrator authentication. On Windows, changing a public network profile to private requires administrator privileges.

## Troubleshooting

- **Provider is not running:** check the provider badge and Status tab. The library location must be saved before sync can start.
- **Resilio shows an API error while its process is running:** LLNG probes the local API several times and, if it remains unreachable, stops and starts the stuck Resilio process. The background watchdog retries recovery with a 20-second minimum interval while sync is desired; a healthy API response cancels the restart.
- **Server discovery fails:** confirm that the devices can reach one another on IPv4 and that the server is running in Server mode. Try entering its IPv4 address manually.
- **Pairing fails:** check that the current code has not expired or been renewed and that Ouisync is running on both devices.
- **Ouisync runs but has no repositories:** use **Check Ouisync** and **Check ng_provider** under Provider UIs → Ouisync. Confirm the trusted bootstrap row is enabled and the repository is attached. LLNG now checks and repairs the built-in `ng_provider` attachment during startup and watchdog cycles. The Ouisync startup log may mention its default user repository folder before LLNG configures its repository store. Check the live Ouisync log and LLNG's `ng_provider_repository_reconcile_result` / `extra_sync_apply_failed` entries to see whether the seed token was accepted or opening failed. Reset the local provider cache only after checking the displayed path.
- **Catalog does not update:** check that the server shares `locallansync` and that the client has completed its initial sync. Invalid or incomplete JSON leaves the previous catalog active.
- **A game does not appear:** confirm the folder is shared, has valid metadata, and does not duplicate a game ID already in a catalog.
- **A game stays unavailable:** verify that the share still exists on the server. LLNG preserves installed copies but pauses unavailable folders.

## Developer interface

The provider abstraction is implemented under `src/core/sync`. LAN discovery and pairing are handled by `src/core/sync/lan_discovery.py`; LAN index publication and import live under `src/core/catalog`.

Relevant routes:

- `GET /sync/status`, `GET /sync/speed`, `GET /sync/providers`
- `GET /sync/providers/ouisync/repositories`
- `GET` and `POST /lan/games` for inventory, sharing, and pairing actions
- `POST /platform/resilio-network-mode` with `{ "mode": "lan" | "internet" }`

Provider paths and connection settings can be overridden in `config/core.json`. Ouisync keys include `ouisync_binary_path`, `ouisync_config_dir`, and `ouisync_log_path`; `lan_mode` selects Client or Server behavior. Resilio keys include `sync_binary_path`, `sync_config_path`, `sync_api_url`, `sync_api_key`, and `sync_license_key_path`. Environment overrides are documented in the sample configuration and release tooling.

On Windows, LLNG passes Resilio the absolute `sync_config_path`. The packaged config lives at `config/resilio/config.json`, while Resilio starts with the install directory as its working directory; passing only `config.json` would make it look in the wrong directory.

Before Resilio starts, LLNG resolves `storage_path` and `pid_file` against the installation root, creates their parent directories, and writes both absolute paths into the runtime config. This also handles Windows installs where the installer does not preserve empty `data/sync` directories.

On Linux, the installer and elevated directory-swap updater assign `config/resilio/` and its contents to the launcher account and grant that account write access. Resilio saves `config.json` by creating a temporary sibling file and atomically replacing the original, which requires directory write permission in addition to write permission on the JSON file.

Ouisync shutdown cancels materialization jobs and waits at most two seconds for an active repository mount. If a mount still holds the lock, LLNG skips graceful session close and terminates the supervised CLI so Windows app shutdown cannot wait indefinitely for that operation.
