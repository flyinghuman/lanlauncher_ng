# ADR-0003 - Native temporary Ouisync mounts on Windows

- ADR ID: ADR-0003
- Title: Use Dokany for short-lived Windows Ouisync repository mounts
- Status: Accepted
- Date: 2026-11-01
- Authors: LANLauncherNG maintainers
- Related Tickets: LLNG-280, LLNG-289, LLNG-290, LLNG-291

## Context

LLNG must install games directly from a per-game Ouisync repository and then release the mount and optionally the repository data. Windows has no built-in user-space filesystem interface equivalent to Linux FUSE. Ouisync's Windows VFS backend uses Dokany; the CLI's VFS feature needs both the matching Dokan user-mode DLL and an installed, signed Dokan kernel driver. The driver installation changes system state and requires administrator privileges. The application installer already runs elevated.

## Decision

- Build the pinned Ouisync CLI (v0.10.2 plus `vendor/licenses/ouisync/LLNG-MODIFICATIONS.patch`) for `x86_64-pc-windows-msvc` with `vfs` enabled and include the generated Dokan 2.3 user-mode DLL and required `VCRUNTIME140.dll` beside the CLI. Reuse the Microsoft runtime DLL from the already bundled CPython distribution and retain its redistribution terms.
- Bundle the official x64 Dokany 2.3.0.1000 MSI required by the pinned Ouisync Dokan bindings. The Windows installer explains the component and offers it as a checked-by-default setup task; if a Dokan 2 driver is already installed, skip the MSI rather than replacing a system driver automatically.
- Treat the Dokan driver as a system prerequisite, distinct from each temporary repository mount. LLNG must always unmount each repository after its install/publish operation and must surface a localized mount error if VFS is unavailable.
- Keep Linux on the FUSE VFS build. Do not add a long-running mount or a user-space filesystem service.
- Preserve upstream notices and the MIT/LGPL license texts for the generated Dokan DLL and its Rust wrapper. Pin binary hashes, source revision, and Dokany installer version in the bundle manifest and build documentation.

## Options Considered

- Keep the Windows CLI without VFS and download/materialize repository content through a second file-transfer implementation.
- Require users to install Dokany manually from a separate download.
- Bundle and install the upstream Dokany runtime through the LLNG Windows setup.

## Rationale

The current Ouisync session API exposes mounts rather than a complete file-export API. A second transfer implementation would duplicate provider behavior and bypass the requested direct archive extraction. Manual Dokany setup would make the default installation incomplete. Bundling the upstream signed installer gives LLNG the same system component used by Ouisync's Windows VFS while keeping per-game mounts temporary.

## Consequences

### Positive

- Windows installs and local LAN publishing can read Ouisync files through the same mount lifecycle as Linux.
- The application can avoid a second full archive copy and can release repository disk space after installation.

### Negative

- Dokany installs a persistent kernel-mode driver and requires administrator approval; the driver remains installed after LLNG game repositories are removed.
- The Windows mount workflow still needs runtime verification on a physical Windows system with the bundled MSI and CLI.
- Dokany license notices and the pinned installer must be included in every Windows distribution.

## Rollout Plan

1. Bundle the VFS-enabled CLI, matching Dokan DLL, official Dokany MSI, hashes, and notices.
2. Add a visible, checked-by-default installer task that skips installation when a Dokan 2 driver is already present.
3. Add Windows validation for driver availability, mount/unmount, install, cancellation, and cleanup before closing LLNG-289.

## Validation

- Rebuild Ouisync v0.10.2 with the LLNG patch applied for the MSVC Windows target with `--features vfs` and validate the executable and DLL as x64 PE files.
- Verify all Windows bundle manifest hashes and license paths.
- On Windows, install with and without an existing Dokan 2 driver, then verify a repository mounts, archive extraction succeeds, and the mount disappears after success, cancellation, and failure.
