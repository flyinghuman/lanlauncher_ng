# ADR-0002 - Offline trust chain for OpenSourceGameIndex distribution

- ADR ID: ADR-0002
- Title: Separate publisher signing and offline revocation from application updates
- Status: Accepted
- Date: 2026-11-01
- Authors: LANLauncherNG maintainers
- Related Tickets: LLNG-269, LLNG-270, LLNG-275

## Context

The global OpenSourceGameIndex catalog can carry Ouisync read tokens. A modified unsigned index must not be able to authorize executable game content or repositories. Clients also need to work in offline LANs, while publishers must be independently authorized and revocable. The application already verifies RSA-SHA256 update manifests without a runtime crypto dependency, but update signing and game publishing have different authorities and consequences.

## Decision

- Use a dedicated game-catalog root public key set embedded in LLNG. Keep its private key offline and separate from all application update keys.
- The root signs a versioned `trusted-publishers.json` registry. The registry may authorize multiple publisher keys for the `game-index` usage and retain revoked keys as tombstones.
- Publishers sign OpenSourceGameIndex v2 snapshots with RSA PKCS#1 v1.5 and SHA-256. The signature covers canonical UTF-8 JSON (sorted keys, compact separators, non-ASCII preserved) with the top-level `signature` member removed. Key IDs select a key in the current trusted registry; the algorithm is declared by that registry.
- Each v2 index has a monotonically increasing `index_revision`. LLNG persists its highest accepted revision and signed-document digest locally and rejects lower revisions or different content at the same revision. Publisher key changes do not reset this counter. This prevents a client that has observed a token rotation or game removal from accepting an older still-validly-signed index.
- Registry sequence numbers increase for each publication. LLNG persists the highest accepted sequence and its content digest in local application state, rejects lower sequences and rejects changed content at the same sequence. This prevents an older synchronized registry from undoing a revocation on a client that has already observed the newer registry.
- A revocation takes effect on a client when the newer root-signed registry reaches that client. Offline clients cannot learn a revocation that has not been delivered; therefore the current registry and signed catalog must be seeded and synchronized with the Ouisync NG provider.
- Token rotation and game removal are published in a higher `index_revision`. A newly provisioned client must be seeded with the latest signed index; a client that has already observed a newer revision rejects replayed snapshots. Publishers must revoke/replace the corresponding Ouisync access when an old read token itself must stop working; removing it from the latest index alone cannot erase a token already copied by a client.
- Schema v1 remains readable for catalog compatibility, but unsigned v1 data cannot authorize Ouisync repository tokens. Only a validated signed v2 index and active publisher key can authorize those tokens.
- A removed key remains listed as revoked. Replacing a compromised key means adding a new key ID in a later root-signed registry and revoking the old ID; key IDs are never reused.
- Ouisync read tokens are secrets in transit and storage: do not log them or include them in ordinary catalog/API payloads. They are only consumed after signature and registry validation.
- Reuse the existing standard-library RSA PKCS#1 v1.5/SHA-256 verification routine for public data verification; private signing remains an offline OpenSSL operation. No runtime dependency is added.

## Consequences

### Positive

- Multiple people can publish through separate keys, and one publisher can be revoked without replacing the update key or every other publisher key.
- Catalog and trust registry distribution remain fully local/offline through the NG provider.
- Registry rollback is blocked after a client has observed a higher sequence.

### Limitations

- A never-connected or freshly reset client cannot know a revocation it has not received. It must receive a current signed registry in its initial seed.
- Root private-key compromise requires a launcher release that replaces the embedded root trust anchor.
- The initial root public key must be provisioned into a launcher release out of band; its private key must never be placed in the repository or the synchronized provider tree.

## Validation

- Validate the machine-readable trust-registry schema and its bounded key/signature fields.
- Test valid, unknown, revoked, malformed, and rollback cases in registry and index runtime verification.
- Keep catalog signing and verification test keys under the test fixture only.
